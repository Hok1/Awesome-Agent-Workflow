# dev-design

## 定位

本 skill 服务于个人开发者的轻量链路（dev 入口），位于需求确认与任务拆分之间。

它用**一份文档**承担设计，目标不是写得更少，而是**写得刚好够开发**：下游 `task-split` 要能据此拆出任务，`task-dev` 要能据此写出代码和测试。

不生成 AR 拆分文档、模块边界文档、独立测试用例设计文档或 `.context` 证据文件。设计只进单份 `dev-design.md`。

唯一的档位就是"写得刚好够开发"这一档；篇幅随需求复杂度自然浮动，不做极简/完整的人工分档。

唯一成果物：

```text
.sdd/{SR}/dev-design.md
```

## 设计总原则

1. **取证实于提问**：能不能改造、改哪里、影响多大，只有跑完代码取证才知道。因此 ASIS 取证**必经**，不是"涉及改造现有代码才做"的可选项。
2. **探索先于提问**：固定顺序 需求 → 架构 → 代码取证 → 写现状 → 提问 → 设计。取证结果落进文档后，再基于事实提问。
3. **能查的不问**：代码能回答的问题（现有行为、调用链、字段结构、接口）一律不问用户；只问代码证不出来、确实需要用户拍板的事。
4. **现状证据写入文档**：现状摘要（几句话）放需求与方案之间作为推理起点；全量取证细节放文末「现状附录」。

## 具体流程

### Phase 1：读需求与架构

1. 读取工作单 `input` 中存在的 `requirement.md`（用户原始需求）和 `software_architecture.md`（软件架构），两者都是可选，缺失不阻断。
2. 用它们确定取证的范围边界：
   - 需求给出本次要做什么、涉及什么能力；
   - 架构文档存在时，用它识别相关模块/分层/边界；
   - 架构文档缺失时，**不能中断**，从需求文本 + 代码结构自行推断探索边界，并在文档「现状摘要」中记录"无架构基线"。
3. 只读取与需求相关的内容，不做无关模块的全景分析。

### Phase 2：代码取证（ASIS，必经）

在向用户提问**之前**完成。取证必须基于真实读到的代码，不得凭文件名、函数名或记忆推测现有行为。

1. 定位需求涉及的代码位置：文件、函数、组件、调用链、数据流。
2. 读取真实实现，确认：
   - 现有行为与逻辑；
   - 关键函数、数据结构、接口的当前签名与语义；
   - 调用链与依赖关系；
   - 已存在的测试覆盖；
   - 隐藏约束、配置项、既有约定。
3. 无法从代码确认的事实，在「现状附录」中标记为待确认，**不要写成既定事实**。
4. 取证只覆盖与本次需求相关的范围，不做与需求无关的模块全景取证。

### Phase 3：写现状摘要与附录

把取证结果写进文档，作为后续提问与设计的共同基础。这是本次需求与方案推理的出发点。

1. **现状摘要**：放在「需求」之后、「方案」之前的 `## 现状` 章节，用几句话给出全量现状的核心结论——现有实现怎么满足（或不满足）本次需求、关键改造点在哪、有无架构基线。让不读附录的人立刻抓住现状。
2. **现状附录**：放在文档末尾 `## 现状附录`，记录取证到的全量细节——需求映射到的代码位置、函数、调用链、数据结构、现有测试、约束。范围是"与本次需求相关的尽量全"，不做无关模块分析。
3. 摘要与附录必须一致：摘要是附录的提炼，不得与附录结论矛盾。
4. 若软件架构缺失，在摘要中写明"无架构基线，探索边界由需求文本与代码结构推断"。

### Phase 4：基于取证结果提问

**在取证与文档现状落盘之后**才向用户提问。提问边界：

- **不问**：代码能回答的问题（现有行为、调用链、字段结构、接口语义）——这些已由取证覆盖；
- **只问**：代码证不出来、确实需要用户拍板的事，例如：
  - 需求目标或范围边界仍不清；
  - 存在多个合理方案且取舍影响较大，且无法从代码/架构推断取舍依据；
  - 涉及外部系统、数据格式、兼容性或验收口径；
  - 需要用户对外部约束、优先级做决策。

提问规则：

1. 逐个问，一次问一个，不要一次抛出问题清单。
2. 用户明确表示“你决定”时，选择最简单可行的方案，记录该决策及理由。
3. 能自己查证的问题（通常是代码）绝不抛给用户。

### Phase 5：写入设计

按合并模板 `references/dev-design.md.tpl` 的章节结构写入真实内容，移除占位提示。

1. 需求：目标与范围边界，含明确的不做什么。
2. 现状摘要：承接 Phase 3，几句话给出现状结论。
3. 方案：给出**明确选择**，不能停留在"可以 A 也可以 B"；备选方案写明选了哪个、为什么；基于现状摘要推导，避免脱离现状凭空设计。
4. 契约变更：新增/修改的接口、数据结构、配置、错误码、CLI 参数等，逐项写全名称、位置、签名/字段、类型、调用方、错误语义、兼容策略。下游 `task-dev` 直接照此实现，含糊即返工。
5. 影响面：列出实际要改动的文件路径；路径经过代码确认，不写猜测路径。
6. 验收标准：可执行、可判定。dev 入口没有独立测试用例设计文档，验收标准同时承担测试规格角色，每条写清验证什么、怎么验证、预期结果。
7. 存疑：仍未解决、影响实现或验证的问题；读者能据此判断或回到用户确认。
8. 现状附录：承接 Phase 3，全量取证细节。

### Phase 6：自检

按「自检清单」逐项核对，不通过则补齐后再交付。

## 文档结构（合并模板）

```text
# {需求名称}·dev 设计
## 1. 需求            —— 目标、范围边界、不做什么
## 2. 现状摘要        —— 几句话的现状核心结论（含无架构基线说明）
## 3. 方案            —— 明确方案选择与理由，承接现状摘要
## 4. 契约变更        —— 逐项写全（无则省略该节）
## 5. 影响面          —— 经代码确认的文件路径
## 6. 验收标准        —— 可执行可判定，承担测试规格
## 7. 存疑            —— 未决问题（无则省略）
## 8. 现状附录        —— 与本次需求相关的全量取证细节
```

## 文档边界

### 必须写入

- 需求目标与范围边界（含明确的不做什么）；
- 现状摘要（几句话）+ 现状附录（与本次需求相关的取证全量）；
- 选定方案及关键决策理由；
- 契约变更（接口、数据结构、配置、错误码、CLI 参数等）；
- 影响的文件或模块；
- 可执行的验收标准；
- 存疑项（如有）。

### 不要写入

- 逐行代码实现或完整代码块（片段示意可以，整段实现不行）；
- 与本次需求无关的模块全景分析；
- 从模板抄来的空章节；
- 未经代码确认的推测性结论；
- 与现状附录冲突的现状描述。

## 完成条件

- `dev-design.md` 存在且通过自检；
- 代码取证已完成且现状附录充分；
- 关键决策已确认，不存在阻断实现的存疑；
- 用户已确认设计方向，或成果明确标记为草案。
