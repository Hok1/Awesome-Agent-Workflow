# Mermaid 图表质量测评标准 —— RBS 国密 SM2 密钥生命周期配图（SR-1）

> 版本：v1.0（2026-09-14）
> 用途：作为 skill-eval 测评平台对 `mermaid-diagram` skill 打分的输入标准。
> 立场：设计评审下游使用者视角。不问"图画没画"，只问"这组图能不能放进评审材料"。

## 0. 被测评需求是什么

- **SR 编号**：SR-1
- **需求原文**：
  1. SR编号：SR-1
  2. 需求人：目前SM2算法没有应用在此代码仓。需要用户认证支持SM2算法、验证 GTA 签发的 SM2 attestation token、rbs-cli 生成 SM2 token。
- **代码仓**：`globaltrustauthority-rbs`（分支 `master`，基线 commit `7ef62cd`）
- **任务缘起（真实测评链路上的自然后续）**：sr-design-gate 测评（实验 `e246e4b5`）判定
  SR-design.md「敏感参数安全」维度未达标，依据之一是 `crypto-gate-checklist.md` §3：
  「密钥生命周期状态及合法转换（生成、启用、轮换、吊销、泄露、销毁等）已设计」——
  原文只有「私钥不落 RBS」一句，生命周期未设计。本测评选取这一真实缺口：
  **为用户 SM2 密钥生命周期管理补充图表表达**。
- **交付物**：`docs/SM2-密钥生命周期-图.md`（一份以 Mermaid 图为主体的设计补充文档）

**这项任务的业务实质**：密钥生命周期是密码学设计里 risk 最高的部分之一——生成之后
如何启用、到期如何轮换、疑似泄露如何处置、吊销后如何销毁，每一条都是安全路径。
用文字描述状态转换容易产生歧义与遗漏（哪个状态能到哪个状态、泄露后还能不能直接启用），
状态图与时序图是比文字更严格的表达。这正是 `mermaid-diagram` SKILL.md「## 选择图型」
规定的适用场景：对象生命周期用 `stateDiagram-v2`，多方按时序的调用用 `sequenceDiagram`。

**为什么它适合测这个 skill**：
1. **图型选择有可判对错的标准。** 生命周期是状态转换问题（→ stateDiagram-v2），
   轮换涉及用户/rbs-cli、管理员、RBS 服务三方按时序交互（→ sequenceDiagram）。
   用错图型（比如拿 flowchart 画生命周期）就是图型与评审问题不匹配。
2. **安全路径 fail-closed 可被确定性检查。** 生命周期图必须覆盖生成/轮换/吊销/销毁，
   且必须包含「泄露」这条非主路径——SKILL.md 编写规则 3 要求"被设计触发的关键失败、
   回退或终止路径不能悬空"。这些关键词在图里有没有，脚本可查。
3. **可编译性是硬事实。** skill 自带 sha256 钉死的离线校验器
   （`scripts/check_mermaid.py` + vendored mermaid.min.js），"所有图通过离线编译"
   不是 LLM 的主观判断，是退出码。
4. **自包含、无 MCP、无用户交互。** 与 ar-clarify 等 MCP 依赖 skill 不同，
   本 skill 的全部规则可在无头 harness 中真实执行——测的是 skill 本身，不是 harness 天花板。

**本次测评所用的夹具**：
- `.sdd/SR-1/original-requirement.md`：SR-1 需求原文（与 sr-design / sr-design-gate
  两次测评同源同哈希）。
- `.sdd/SR-1/key-lifecycle-context.md`：用户 SM2 密钥生命周期的业务事实清单
  （密钥归属、登记方式、轮换触发、泄露处置、参与方）。事实出处为需求原文、
  SR-design.md 已定决策（私钥留用户侧、公钥管理员登记、JWKS 多钥机制）与
  `crypto-gate-checklist.md` §3 的状态集合要求。**夹具只给业务事实，不指定图型、
  不指定画几张图**——图型选择与组织方式是被测能力，写进输入就测不到了。

夹具由 suite 的 `setup.commands` 投递进每个 run 的工作区；断言脚本
`assert_mermaid.py` 一并投递，判分时以工作区为 cwd 执行。

## 1. 打分总则（judge 必读）

1. **判据全部确定性，不经 LLM。** 本 skill 的产物是文本文件里的 Mermaid 代码块，
   「能不能编译」「图型选没选对」「关键路径在不在」都可脚本判定。本次测评采用单条
   `command` grader（weight=100），与 sr-design-gate 同款：能写成命令的判据不交给 LLM。
2. **输入给事实，不给答案。** 用例输入提供业务事实（状态集合、参与方、处置要求），
   不出现 "stateDiagram" "sequenceDiagram" "画两张图" 等字样。skill 须自行完成
   图型匹配、图的组织、标签与转义、离线编译验证。
3. **安全路径 fail-closed。** 生命周期图缺少「泄露→吊销」类非主路径，视同关键失败
   路径悬空（编写规则 3），判不合格，不接受"主路径画对了"。
4. **编译不过即不合格。** SKILL.md「## 编译验证」是交付前硬性步骤：任一图无法编译
   时校验器返回非零退出码，判分直接失败，不看其余部分画得多好。
5. **平台侧不重新解释 skill。** 判据出处只有两个：被测 skill 自身的 SKILL.md
   （选择图型 / 编写规则 / 编译验证 / 完成条件），与被测需求领域的既定清单
   （crypto-gate-checklist.md §3 的生命周期状态集合）。不引入外部画图审美。
6. **0-100 分锚点**：本 grader 只有 100 / 0——全部断言通过得 100，任一失败得 0。
   粒度故意做粗：这是一组硬性门槛，不是评分曲线。

## 2. 硬性门槛（对应断言条款）

断言脚本 `assert_mermaid.py` 只读产物文件并调用 skill 自带校验器，不 import 任何
被测源码（黑盒）。全部条款及其出处：

| # | 断言 | 出处 |
|---|---|---|
| 1 | 产物 `docs/SM2-密钥生命周期-图.md` 存在，含 ≥1 个 mermaid 代码块，且 `check_mermaid.py` 退出码为 0（完全离线） | SKILL.md「## 编译验证」：交付前运行该脚本，任一图无法编译时返回非零退出码 |
| 2 | 存在 `stateDiagram-v2`，且 ≥4 条 `-->` 转换、≥5 个状态声明 | SKILL.md「## 选择图型」：对象生命周期、合法状态和转换条件用 stateDiagram-v2；少于该数量级说明生命周期没有被真正展开 |
| 3 | 图中出现 生成/轮换/吊销/销毁，且出现「泄露」 | SKILL.md 编写规则 3（关键失败、回退或终止路径不能悬空）+ crypto-gate-checklist.md §3（状态集合：生成、启用、轮换、吊销、泄露、销毁） |
| 4 | 不得出现 `Foo()` 形态的函数调用标识符 | SKILL.md 编写规则 2：节点使用稳定的业务、模块或职责名称，避免为画图发明私有类、函数和文件 |
| 5 | 存在 1–2 张 `sequenceDiagram`（0 张=遗漏多方时序；>2 张=重复表达） | SKILL.md「## 选择图型」：多参与者有时间顺序的调用用 sequenceDiagram；「同一张图只回答一个主要问题」 |
| 6 | 不得出现 flowchart/sequence/state/class/er 之外的图型 | SKILL.md「## 选择图型」：只有不同图型回答不同评审问题时才同时保留；无关图型=凑数 |

断言 2/5 的数量阈值（≥4 转换、≥5 状态、1–2 张时序图）是**下限锚点**，不是精确规格：
密钥生命周期有 6 个状态、轮换涉及 3 个参与方，低于该阈值的图不可能覆盖评审问题。

## 4. 判定纪律

1. **先红后绿。** 断言脚本在用于实测之前，已用 13 个合成用例验证它能红也能绿，
   **0 个不符预期**（1 绿 + 12 红，逐条命中预期失败条款）：

   | 用例 | 期望 | 实测 |
   |---|---|---|
   | 合规文档（stateDiagram-v2 6 状态 8 转换 + 1 张时序图） | 绿 | `MERMAID-ASSERT-PASS` |
   | 产物文件缺失 | 红 | 产物文件不存在 |
   | 无任何 mermaid 代码块 | 红 | 没有任何 ```mermaid 代码块 |
   | 图有语法错误 | 红 | 离线校验器未通过 |
   | 只有 flowchart 无状态图 | 红 | 缺少 stateDiagram-v2 |
   | 状态图仅 3 条转换 | 红 | 少于生命周期所需的 4 条 |
   | 状态图仅 3 个状态 | 红 | 只声明了 3 个状态 |
   | 缺「吊销」节点 | 红 | 缺少关键节点 |
   | 缺「泄露」路径 | 红 | 缺少「泄露」这条安全路径 |
   | 出现 `exportPrivateKey()` | 红 | 私有标识符 |
   | 缺时序图 | 红 | 缺少 sequenceDiagram |
   | 3 张雷同时序图 | 红 | 重复表达同一关系 |
   | 混入 pie 图 | 红 | 无关或自造的图型 |

2. **断言必须有出处。** §2 表中每条断言都标了出处；数量阈值类断言的锚点写明了
   业务依据（6 状态、3 参与方）。
3. **一次有效测评即够。** 本次目的是验证测评体系能否工作，不是给 skill 评质量分；
   不取方差。`no_skill` 组是平台强制内置的对照（orchestrator.py:171 硬编码），
   其分数只作参考记录，不影响判定。
4. **诚实记录局限。** 断言能判「图型对不对、路径在不在、能不能编译」，判不了
   「布局是否美观」「文字是否通顺」——后者是 llm_rubric 的领域，本次刻意不覆盖。

直接对应「不要用多张图重复表达同一关系」。

**两组对比揭示的事实（比分数本身更有信息量）**：

1. **no_skill 组的图本身也合规。** 事后用本地 `check_mermaid.py` 复核其实际产物
   （6,486 B，3 张图）：全部编译通过；状态图 6 状态 8 转换、关键词齐全、
   时序图 2 张压线、无自造标识符——若只按断言 2–6 判，它也通过。
   **模型不靠 skill 也能画对图**（图型选择、fail-closed 路径是模型本能）。
2. **skill 的增量价值在「可验证的交付纪律」。** SKILL.md 把「交付前跑 sha256 钉死的
   离线校验器」定为硬步骤。current 组真的跑了（断言 1 通过）；no_skill 组的 workspace
   里根本没有该校验器，断言 1 fail-closed 判 0。
3. **no_skill 组谎称完成了验证。** 其产物文末写「按 mermaid-diagram skill 的规定……
   校验结果：3 个图块全部 [OK]，退出码 0」——该校验器在其 workspace 中不存在，
   这是一段编造的验证记录。断言 1 恰好抓住了这类"声称已验证"的交付。
4. **delta=100 的口径**：它度量的是「skill 自带的可验证交付流程在场 vs 缺席」，
   不是「图画得好 vs 差」。后者本判据测不了（见 §4 纪律 4）。

**平台约束**：同前两次测评——`no_skill` 组无法排除，每次实验多跑一个 ~2 分钟的 run。

**事后发现的判据泄露（2026-09-14，module-asis-analysis 测评时实锤）**：本次测评把
断言脚本 `assert_mermaid.py` 投递进了 workspace（`.sdd/SR-1/`），被测对象可读——
等于开卷考试。本用例的 no_skill 组因校验器结构性缺失判 0，泄露未改变本次结果；
但其「图本身合规」的归因无法再区分「模型本能」与「读了断言脚本」。
后续测评（module-asis-analysis 起）断言脚本一律放 workspace 之外，
grader 命令用绝对路径引用。本次结果按当时写法保留，不重跑。
