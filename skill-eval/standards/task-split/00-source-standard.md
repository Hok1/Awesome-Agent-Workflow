# 任务拆分质量测评标准 —— RBS 国密 SM2 / rbs-core（SR-1）

> 版本：v1.0（2026-09-14）
> 用途：作为 skill-eval 测评平台对 `task-split` skill 打分的输入标准。
> 立场：AICoding 执行者与评审者的下游视角。不问"任务列没列"，只问
> "这份计划能不能直接指导串行实现且不丢验证"。

---

## 0. 被测评需求是什么

- **SR 编号**：SR-1（RBS 国密 SM2 需求链路的第八个测评点）
- **代码仓**：`globaltrustauthority-rbs`（基线 commit `7ef62cd`）
- **交付物**：`.sdd/SR-1/{AR}/{模块组名}/tasks-overview.md`（yaml required output）
- **输入**：本链路真实上游产物——说明书（module-tobe-design `95b8f3c3` current）、
  测试设计（module-test-design `2305ce3a` current，TC1–TC27）、门禁结果
  （module-design-gate clean 用例中**结论为通过**的真实报告）。

**这项任务的业务实质**：task-split 把设计与验证规格收敛为可串行执行的薄任务计划。
它的反面典型：把设计文档重写一遍（计划变成第二份说明书）、按技术层切薄任务
（每个任务都走一遍完整流程，成本倍增）、丢用例（测试设计了 27 条，计划只验 20 条）、
生成一堆独立任务文件（契约禁止）。本 skill 的「任务计划边界（允许/禁止写入）」
和「拆分原则 8 条」几乎全是可确定性检查的形态契约。

**可测性**：无 MCP；「交给用户检查」环节在无头模式下走「视为草案」合规路径。
判据保密纪律同上：断言脚本不进 workspace、task 不复述 skill 规则。

---

## 1. 打分总则

1. **判据全部确定性。** 单条 `command` grader（weight=100），workspace 外执行。
2. **0-100 分锚点**：全过 100，任一失败 0。
3. **一次有效测评即够。** no_skill 组仅作参考。
4. **诚实记录局限。** 断言能判「形态、覆盖完整、禁区」，判不了「拆得好不好」
   （任务粒度是否合理、依赖排序是否最优——属评审判断，本次刻意不覆盖）。

---

## 2. 硬性门槛（对应断言条款）

| # | 断言 | 出处 |
|---|---|---|
| 1 | `tasks-overview.md` 存在于契约路径 | yaml output required |
| 2 | 无任何 `T\d+-*.md` 独立任务文件 | 任务计划边界·禁止写入「生成独立 T[N]-*.md 任务文件」 |
| 3 | 三输入 sha1 不变 | 输入只读（Phase 1「完整读取」无语义授权改写） |
| 4 | 模板骨架章节齐全（元信息/执行规则/串行执行顺序/任务计划/存疑汇总/待处理用例登记/执行记录） | overview_template.md 固定骨架；Phase 4「不得从空白文档自由发挥」 |
| 5 | 任务计划表六列形态，编号 T1 起连续；「做什么/改哪些文件」列不得近乎为空 | 模板任务计划表；拆分原则 4「编号必须与执行顺序一致」 |
| 6 | 测试设计的 TC 编号全集（由输入自身给出）⊆ overview 引用集 | 拆分原则 7「覆盖完整」 |
| 7 | 「存疑汇总」章节无未决内容（空/「无」；出现 待确认/待定/？ 即红） | 拆分原则 8「存疑不放行……未清零前不得确认计划」 |

## 3. 判据落点

单条 `command` grader：`python C:\tmp\ctx5ts\assert_tasksplit.py`，
cwd = run 工作区，退出码 0 得 100，非 0 得 0。

## 4. 判定纪律

1. **先红后绿。** 10 个合成用例（1 绿 + 9 红），0 个不符预期；见 `fixture/redgreen/`。
2. **断言必须有出处。** §2 逐条标注；断言 6 的合法域由测试设计输入动态提取
   （不写死 TC 数量）。
3. **范围控制。** 不评拆分优劣，只评契约与覆盖。
