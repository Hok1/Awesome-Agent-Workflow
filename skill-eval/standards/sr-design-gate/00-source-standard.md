# SR 设计门禁质量测评标准 —— RBS 国密 SM2 算法支持（SR-1）

> 版本：v1.0（2026-09-14）
> 用途：作为 skill-eval 测评平台对 `sr-design-gate` skill 打分的输入标准。
> 立场：门禁下游使用者视角。不问"报告写没写"，只问"这份门禁结论能不能托付"。

---

## 0. 被测评需求是什么

- **SR 编号**：SR-1
- **需求原文**：
  1. SR编号：SR-1
  2. 需求人：目前SM2算法没有应用在此代码仓。需要用户认证支持SM2算法、验证 GTA 签发的 SM2 attestation token、rbs-cli 生成 SM2 token。
- **代码仓**：`globaltrustauthority-rbs`（分支 `master`，基线 commit `7ef62cd`）
- **被检查的输入**：`.sdd/SR-1/SR-design.md`（一份**已带缺陷**的 SM2 设计文档）
- **交付物**：`.sdd/SR-1/SR-design-gate.md`（门禁报告）+ `.sdd/SR-1/gate-data.json`（回传数据）

**这项需求的业务实质**：`sr-design-gate` 不是设计者，是**守门人**。它读一份别人写好的 SR 设计，
判定这份设计能不能进入 `ar-split`（需求拆分）——`flow.yaml` 里 `sr-design-gate` 是个 `choice` 节点，
只有 `data.gate_result == 'pass'` 才放行到 `ar-split`，`fail`/`blocked` 一律拦下并给出拒绝理由。

**为什么它风险高**：
1. **误判的两个方向都会造成实际损失。** 漏判（该拦的放行）把带 P0 的设计送进开发，问题在客户现场
   或验收阶段才暴露；误拦（不该拦的拦下）会让整条流水线停摆，且比漏判更容易被"绕过门禁"的动机消解掉。
   门禁的价值全在于它的判定与依据是否能被复核。
2. **它是整条流水线上唯一的自动化否决点。** 门禁之后是拆分、设计、编码、测试；门禁是这些环节之前
   最后一次"以文档形态拦住错误"的机会。它一旦失效，后续每一环都在为错误设计买单。
3. **判定依赖可追溯的依据，而不是印象。** 门禁的每个维度判定和每条冲突都必须能指回被检查文档的
   具体位置或检查清单的具体条款。一份"结论正确但说不出依据"的门禁报告，在工程上等于没有门禁。

**本次测评所用的夹具（`C:\tmp\ctx4gate\SR-design.md`）**：取自 sr-design 实测产出的 v1 文档，
其中**刻意保留**了 5 条未达标缺陷（分布在 3 个准入维度上，详见 §2 HG-3）：

- 主动植入的：私钥导出接口无导出策略（crypto §5，P0）、该接口的输出/错误/治理契约缺失
  （契约完整性）、图例含未使用状态 + 变更连线未着色（图表变更表达）
- 文档原生的：SM2 签名 k 值/随机源未识别（crypto §2）、用户 SM2 密钥生命周期未设计（crypto §3）
  —— 这两条是 sr-design 产出时就存在的，未经我改动，但同样是清单明文规定的未达标项

夹具由 suite 的 `setup.commands` 投递进每个 run 的工作区，被测 skill 只负责读它、判它、写报告。

**夹具刻意保留的干扰项（用于检验降级口径）**：本仓库没有 `.sdd/software_architecture.md`。
`gate-checklist.md` 准入维度表明文规定此时「改判 `降级检查（无架构基线）`，仅核对 SR 设计内部自洽性，
并记 P2 待补项」——**不是未达标**。把这一情形误判为未达标，即为判定错误。

## 1. 打分总则（judge 必读）

1. **结论与计数必须自洽。** `gate_result` 与六个 `summary` 计数是同一件事的两种表达。任何一个组合
   出现"结论说 fail 但计数全零"这类自相矛盾，判该次运行不合格。
2. **判定必须带得出处的依据。** 报告中的每个维度判定、每条冲突，都必须引用被检查文档的章节/位置或
   检查清单的条款。只有结论没有依据的判定视为无效判定——这条同时意味着"结论对但依据假"不能得分。
3. **漏判与误拦都扣分，但漏判更重。** 漏判 P0 直接把风险放进下游；误拦一个合格设计只是浪费一次往返。
   两者都必须显式记录，不得只看"有没有拦下来"。
4. **诚实加分。** 明确写出"不适用：<可追溯依据>"（例如架构基线缺失时改判 `降级检查（无架构基线）`、
   并记 P2 待补项）是**正确行为**，不扣分。把降级写成"未达标"或反之，都是判定错误。
5. **平台侧不重新解释 skill。** 本标准的判据全部来自被测 skill 自身的契约文件
   （`SKILL.md`、`definitions/sr-design-gate.yaml`、`definitions/flow.yaml`、
   `references/gate-checklist.md`、`references/crypto-gate-checklist.md`），不引入外部评价口径。
6. **0-100 分锚点**：90+ = 结论、计数、依据三者全部正确且可复核；70-89 = 结论正确，个别依据或
   计数有偏差；50-69 = 结论勉强对但依据不可依赖；30-49 = 判定形式完整、实质空转；<30 = 结论错误
   或产物缺失。

## 2. 硬性门槛（一票否决项）

以下四项各自独立判定**通过 / 不通过**，不通过即说明这次门禁不能托付。

### HG-1 交付物必须齐备且符合 work-order 契约

`definitions/sr-design-gate.yaml` 规定输出 `.sdd/{SR}/SR-design-gate.md` 为必填。
`SKILL.md` 规定 `report` 恒为实际报告路径、**不得填 `null`**。

**判不通过的情形**：报告文件缺失或近乎为空；`gate-data.json` 缺失或不是合法 JSON；
四个必备字段（`gate_result`/`recommendation`/`report`/`summary`）缺任一项；`report` 为 `null`
或未指向 `SR-design-gate.md`。

### HG-2 结论必须与夹具事实一致（不得漏判 P0）

夹具中存在 `crypto-gate-checklist.md` §5 明确规定的 P0：新增了私钥导出接口
（`--export-private-key`，把 SM2 私钥以 PEM 写出到目标路径），但**全文未声明任何导出策略**。
清单原文："存在此类接口但完全未声明导出策略：记 P0"。

**判不通过的情形**：`gate_result` 为 `pass`；或结论非 pass 但 `p0_conflicts == 0`。

### HG-3 未达标维度计数必须等于 3（准入维度表粒度）

`summary.unqualified_dimensions` 应按**准入维度表**（`gate-checklist.md` 12 个维度）计数，
本次测评钉死为 **3**：

1. **敏感参数安全** —— crypto 专项清单在该维度下有**三个检查节**同时未达标，但**归为同一个维度**：
   - §5 导出接口策略：新增私钥导出接口 `--export-private-key` 而全文无导出策略 → **P0**
   - §2 识别完备性：末句「缺项即维度未达标」；夹具未识别 SM2 签名一次性随机数 **k 值及其随机源**，
     亦无敏感参数来源/存储清单（清单 §2 第 4 项点名「签名 k 值」）
   - §3 架构级密钥管理决策：清单要求「密钥生命周期状态及合法转换（生成/启用/轮换/吊销/泄露/销毁）
     已设计」；夹具仅有「私钥不落 RBS」一句，用户 SM2 密钥生命周期未设计
2. **契约完整性** —— `gate-checklist.md` §9「接口契约完整性判定」第 2、3、4 条：同一个导出接口
   既无输出产物契约（条 2），也无错误模型（条 3：路径不可写/文件已存在/与 `--private-key-file`
   同给的语义），也无治理属性（条 4：鉴权、幂等、超时、重试、版本兼容性）。
   清单明文：「任一适用项缺失…记 P1 且「契约完整性」未达标」
3. **图表变更表达** —— 图表检查规则 5（图例列出了「删除」但图中无删除对象）+ 规则 6
   （9 个节点标为 changed，但所有连线只有新增/不变两色，属"只给节点着色而遗漏连线"）

**关键区分：维度数 ≠ 缺陷条数。** 夹具的未达标**缺陷条数**是 5（crypto §2、§3、§5 三条，
加契约完整性、图表变更表达各一条），而它们落在 **3 个准入维度**上——crypto §2/§3/§5 三条
都是「敏感参数安全」这一个维度内部的检查节。断言钉的是**维度数 3**。
（此口径由实测确认：`current` 组报告在「密码学专项复核」表中把 §2/§3/§5 分别标为「未达标」，
在「维度检查」表中汇总为「敏感参数安全」一个未达标维度，与 `summary.unqualified_dimensions=3` 自洽。）

**判不通过的情形**：`unqualified_dimensions != 3`。

**不作为本门槛的情形**：架构基线缺失导致的 `降级检查（无架构基线）` 与 P2 待补项
（`gate-checklist.md` 准入维度表明文规定该情形不判未达标）。夹具刻意保留此情形，
用于检验被测 skill 是否会把合法降级误判为未达标——本次实测中它**没有**误判。

### HG-4 报告正文必须落到具体维度名（依据可复核）

报告必须按维度逐个给出判定，且必须覆盖上述三个维度名。

**判不通过的情形**：报告未出现「敏感参数安全」/「契约完整性」/「图表变更表达」中任一维度名；
或维度判定只有结论、引用不到被检查文档的位置或检查清单的条款。

## 3. 判据落点（本次测评只评测以下一组）

本 skill 的判据**不需要 LLM 判读**。门禁的产物是结构化数据（`gate-data.json` 的四个字段 + 六个计数）
加一份文本报告，两者都可以用确定性断言读完。因此本次测评采用**单条 `command` grader**，
以 `weight=100` 参与质量分，不加权给任何主观判据——这是相对 sr-design 那一版（11 条全 `llm_rubric`）
的定向改进：能写成命令的判据，不交给 LLM。

断言脚本 `.sdd/SR-1/assert_gate.py` 只读两个产物文件，不 import 任何被测源码（黑盒），
按 §2 的四道门槛逐条断言，全部通过才输出 `GATE-ASSERT-PASS` 并 `exit 0`。

## 4. 判定纪律

1. **先红后绿。** 断言脚本在用于实测之前，已用合成用例验证过它能红、也能绿（详见归档
   `03-graders.md` 与实验记录）。未经红绿验证的断言不得用于判分。
2. **夹具缺陷必须可反查。** 每处植入的缺陷都必须在检查清单里能找到明确判定条款，否则不构成
   "未达标"的依据，只是设计者的个人偏好。
3. **降级不等于未达标。** 架构基线缺失时，`gate-checklist.md` 明确规定改判"降级检查（无架构基线）"
   并记 P2 待补项——这种情况**不得**计入 `unqualified_dimensions`。夹具刻意保留了这一情形，
   用于检验被测 skill 是否会把合法的降级误判为未达标。
4. **一次有效测评即够。** 本次目的是验证测评体系能否工作，不是给 skill 评质量分；不取方差，
   不做对照组。
