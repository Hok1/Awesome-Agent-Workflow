# 模块设计门禁质量测评标准 —— RBS 国密 SM2 / rbs-core（SR-1，正/反双例）

> 版本：v1.0（2026-09-14）
> 用途：作为 skill-eval 测评平台对 `module-design-gate` skill 打分的输入标准。
> 立场：AICoding 的准入守门人视角。不问"报告写没写"，只问"这份门禁结论能不能
> 决定整条流水线的推进"。

---

## 0. 被测评需求是什么

- **SR 编号**：SR-1（RBS 国密 SM2 需求链路的第七个测评点）
- **代码仓**：`globaltrustauthority-rbs`（基线 commit `7ef62cd`）
- **交付物**：`.sdd/SR-1/{AR}/{模块组名}/.context/模块设计门禁结果.md`（yaml required）
- **输入三件套**：均为本测评链路的真实上游产物——说明书与 context 来自
  module-tobe-design 实验 `95b8f3c3` 的 current 组；测试设计来自 module-test-design
  实验 `2305ce3a` 的 current 组。上游基线 SR-design.md 为 sr-design 测评的真实产出，
  AR-clarify.md 为手写夹具（ar-clarify 是 MCP 依赖 skill，本 harness 不测本体）。

**这项任务的业务实质**：module-design-gate 是模块设计进入 AICoding 之前的唯一
自动化否决点，八维度准入（上游完整性/证据充分性/边界清晰性/决策确定性/契约完整性/
工程可执行性/验证闭环性/风险处置性）+ 三值结论 + 七值建议。它面对的典型爆炸方式：
该拦的放行（带缺陷设计进入编码）、不该拦的拦（流水线停摆）、结论与建议自相矛盾、
引用不存在的编号（伪造依据）、顺手改写被检查的输入（守门人篡改证据）。

**双例设计**（setup 互斥，两个独立 suite）：

- **正向 clean**：真实合规三件套。门禁结论值不预定（夹具含真实的 GTA 侧待确认项，
  判「通过」「不通过」「阻塞」均有可能），断言只钉**形式契约**。
- **反向 defect**：在真实三件套上植入两处有明确判定条款的缺陷——
  1. 说明书 D5 决策的「设计依据摘要」列改为「待定」（SKILL.md 维度未达标常见判定
     第 1 条：影响实现的「待定」未标为非阻断改进项 → 决策确定性）
  2. 测试设计追加概要用例 TC99（只写「补充单测覆盖异常场景」，无四字段——
     SKILL.md 明文「门禁必须判定验证闭环性不通过」）
  期望：结论「不通过」且命中「决策确定性」「验证闭环性」两个维度名。

**判据保密纪律**：断言脚本不进 workspace、task 不复述 skill 规则、不提示夹具
是否有缺陷。

## 1. 打分总则

1. **判据全部确定性。** 每个 suite 单条 `command` grader（weight=100）。
2. **0-100 分锚点**：全过 100，任一失败 0。
3. **正向不钉结论值。** 夹具含真实待确认项，钉结论值等于替门禁做判断；
   形式契约（枚举/一致性/不改输入/编号可反查）才是确定性可判的。
4. **一次有效测评即够。** no_skill 组仅作参考（语料先验已知）。

## 2. 硬性门槛（对应断言条款）

### 正向/反向共用（assert_gate_common.py，6 条）

| # | 断言 | 出处 |
|---|---|---|
| 1 | 门禁结果文件存在于契约路径 | yaml output required |
| 2 | 三输入文件 sha1 不变（gate 不得改写被检查对象） | 成果物协作规则「不得创建、编辑或覆盖」 |
| 3 | 结论 ∈ {通过， 不通过， 阻塞} | 门禁结论「结论只能是」 |
| 4 | 建议 ∈ 七值枚举 | 门禁结论「还必须给出明确的门禁建议」 |
| 5 | 结论-建议一致（通过 ⇔ 可进入 AICoding；不通过 ⇎ 仅可进入） | 「只要存在任一适用维度未达标，门禁结论不得为 通过」 |
| 6 | 报告引用的 D/TC/A/E 编号 ⊆ 对应输入的实际编号域（可反查） | 「门禁引用的……必须来自正式说明书……必须能在证据索引中反查」 |

### 反向追加（assert_gate_defect.py，2 条）

| # | 断言 | 出处 |
|---|---|---|
| 7 | 结论不得为「通过」 | 夹具含两处必须整改缺陷；「不通过：存在必须整改的问题」 |
| 8 | 报告含「决策确定性」且含「验证闭环性」 | 维度表 + 成果物协作规则对概要用例的明文判定 |

**结果**：

| 用例 | 组 | 结论 | 未达标维度 | 判分 |
|---|---|---|---|---|
| clean | current | 不通过 | 验证闭环性 | 100（形式合规） |
| clean | no_skill | 通过 | 无 | 100（形式合规） |
| defect | current | 不通过 | 验证闭环性 | 100（TC99 命中） |
| defect | no_skill | 不通过 | 决策确定性、验证闭环性 | 100（双命中） |

**结果的正确读法**：

1. **正向 current 组判「不通过」是正确行为**：干净三件套的测试设计自认了 5 项缺口
   （GAP3 SM2 测试向量生成方式未定、GAP5 测试连接池、K3/A19 两项 P0 未覆盖）——
   gate 按「验证闭环性」拦下，并给出四条下一轮重试条件。正向用例不钉结论值的
   设计（§1 总则 3）正好容纳了真实缺口。no_skill 组判「通过」——它没有追这些
   缺口，同样形式合规但实质更松。**同分不同质，分差在断言粒度之外，如实记录。**
2. **反向两组都拦住了 TC99**（验证闭环性），分歧在 D5：current 组把
   「结论列=待定 + 状态列=已定稿（本模块）；GTA 侧待确认」读作自洽（本模块已定稿、
   外部待确认），no_skill 组判入决策确定性。两种读法都被规则允许
   （「先做上游/用户确认」是合法建议枚举），故断言 8 只钉无争议的 TC99 条款。

**判据迭代记录**：

| 轮 | 缺陷 | 修正 |
|---|---|---|
| v1/v2 | 断言 3 只认行内「结论：X」，漏 `| 门禁状态 | X |` 表格形态；断言脚本在 GBK 控制台 UnicodeEncodeError | 结论双形态容差（交替序「不通过」在前）；stdout reconfigure UTF-8 |
| v2/v3 | 夹具组装缺陷：gate 需要架构文档作边界基线，setup 漏投，被 gate 正确抓为「证据不可反查」 | 双 suite 加投 `software_architecture.md` |
| v3/v4 | 断言 8 按全文含维度名判定，被「七个维度达标」式过程表骗检（no_skill 组违规输出达标过程表，反而命中） | 改判「未达标维度」**字段值**；红绿补骗检用例 |
| v3/v4 | 缺陷 1 初版只改 D5 依据列，被 gate 合规降级为非阻断项 | 植入提升到设计结论列（「待定」），再交还 gate 判定 |

**顺带的体系观察**：SKILL.md 明文「结果文件只列未达标维度及其问题，不输出
『全部达标』过程表」——no_skill 组在反向 v3 中输出了「七个维度达标」枚举式表述，
违反此条但未被任何断言覆盖（已记录为可加固点，未加断言：一句话总述与
「过程表」的边界难以确定性区分）。
