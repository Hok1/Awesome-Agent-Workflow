# SR 设计文档质量测评标准 —— RBS 国密 SM2 算法支持（SR-1）

> 版本：v1.0（2026-09-11）
> 用途：作为 skill-eval 测评平台对 `sr-design` skill 打分的输入标准。
> 立场：需求设计者视角。不问"文档齐不齐"，只问"照这份文档开工，业务会不会翻车"。

---

## 0. 被测评需求是什么

- **SR 编号**：SR-1
- **需求原文**：
  1. SR编号：SR-1
  2. 需求简介：目前 SM2 算法没有用于此代码仓中。需要在用户认证支持 SM2 算法、验证 GTA 签发的 SM2 attestation token、rbs-cli 生成 SM2 token。
- **代码仓**：`globaltrustauthority-rbs`（分支 `master`，基线 commit `7ef62cd`）
- **交付物**：`.sdd/SR-1/SR-design.md`（由 `sr-design` skill 依据 `reference/design-template.md` 生成）

**这项需求的业务实质**：让 RBS 具备"用国密 SM2 做身份"的能力，从而能部署进要求国密合规（GB/T 32918 / GB/T 32905）的客户环境。三个触点——用户认证走 SM2、校验 GTA 签发的 SM2 attestation token、rbs-cli 能造 SM2 token。

**为什么它风险高**：
1. **互操作是硬约束，且失败发生在客户现场。** RBS 不是 token 的签发方，GTA 才是。RBS 只能被动接受 GTA 的编码约定。约定写错一个字（DER 还是 r‖s、签名输入是否预哈希、Z 值 UserId 取什么），代码全绿、单测全过，一到真实 GTA token 上就验签失败——而此时已经发货。
2. **合规范围没有天然边界。** 客户口中的"支持国密"可能只指签名，也可能连带要求 SM3 独立使用、SM4 加密、双证书体系。范围如果不在设计阶段钉死，验收时就是无底洞。
3. **这是一次信任边界变更。** 引入 SM2 意味着 RBS 要接受一类新的密钥材料与签名格式，密钥泄露的应急路径、无吊销列表的后果，都必须作为业务决策写清楚，而不是藏在运维备注里。

## 1. 打分总则（judge 必读）

1. **逐条判定，不得合并成笼统印象分。** 每个维度按下面的判据独立给分，并在 `evidence` 中引用被评文档的**原文片段或章节编号**。引用不到原文的判定视为无效。
2. **空壳不得分。** 章节标题存在但内容为占位符、套话、或只有表格表头，该维度直接判 **≤30**，无论篇幅多长。
3. **准确比详尽值钱。** 写了但写错的事实，扣分应当**重于**没写。尤其：与代码/契约实际行为相悖的描述，该维度判 **≤20**。
4. **诚实加分。** 明确写出"不适用：<可追溯依据>"、或明确标注"未确认、待澄清"的地方，不扣分（主干章节除外，见 HG-4）。把不确定性写清楚，比编一个答案有价值。
5. **禁止用目录结构冒充内容。** 文档章节齐全、mermaid 图精美，都不是加分项本身；只有它们承载的信息正确且够用时才算。
6. **0-100 分锚点**：90+ = 可直接作为下游开发与验收的唯一依据；70-89 = 基本可用，存在需澄清的缺口；50-69 = 有骨架但关键契约/验收不可依赖；30-49 = 形式完整、实质空转；<30 = 缺失或误导。

## 2. 硬性门槛（一票否决项）

以下四项各自独立判定**通过 / 不通过**，不通过即说明该文档不能作为开发依据，须在结论中显式列出。

### HG-1 交付范围必须钉死
文档必须明确写出本次交付**包含**哪些国密算法能力、**不包含**哪些，并对不包含项给出依据（需求未要求 / 依赖三方件不支持 / 留待后续 SR）。
具体最低要求：至少正面回答 SM2 签名/验签是否包含、SM3 是否作为独立能力（非仅 SM2 内部摘要）交付、SM4 是否在范围内、证书/双证书体系是否涉及。

**判不通过的情形**：只描述要做什么，从不划定边界；或通篇只谈 SM2 但对 SM3/SM4/证书的处置完全沉默，导致验收范围无法确定。

### HG-2 GTA 签名契约必须精确到可互操作
文档必须把"RBS 如何校验 GTA 签发的 SM2 token"写到一个工程师能据此直接实现的程度，且关键约定**不得与代码现有事实相矛盾**。必须覆盖：签名值的编码形式、签名输入的字节范围、SM3 的 Z 值（UserId）取值、算法标识与白名单、公钥格式与分发方式、时钟容差。

**判不通过的情形**：缺少上述任一项；或写了但与仓库现有实现/契约（如 `rbs/core/src/auth/authn/sm2_algorithm.rs` 中的签名格式处理）相矛盾；或关键项写成"参照标准"而无具体取值。

### HG-3 关键规格必须逐条可验收
文档"关键规格"章节中的每一条量化规格，都必须映射到验收用例编号；且该用例必须是**能真正证伪这条规格**的黑盒用例（用外部手段驱动、断言在系统外表面）。

**判不通过的情形**：出现无法被任何用例验证的规格；或用例引用了却根本不具备验证该规格能力（例如规格讲 Z 值，引用的用例却是"注册后凭 token 访问成功"这种对 Z 值不敏感的连通性用例）；或存在规格未被任何用例覆盖。

### HG-4 验收必须闭环
验收用例集必须覆盖六类对象（① 功能主成功场景 ② 异常/冲突/兼容场景 ③ 对外接口契约 ④ 数据一致性 ⑤ DFX 量化阈值 ⑥ 原始需求明确要求的可验收行为），且"主流程 / 功能定位 / 对外接口 / 关键规格 / 模块划分与职责 / SR 整体验收标准"六个主干章节不得标注"不适用"。每个原始需求触点都必须有对应用例。

**判不通过的情形**：六类对象缺任一类；主干章节被判"不适用"；三个原始需求触点（用户认证支持 SM2 / 验证 GTA SM2 token / rbs-cli 生成 SM2 token）有任一无对应用例。

## 3. 加权维度（合计 100 分）

### D1 业务范围与合规边界 · 权重 15
判的是：一个没参与需求的读者，能否从文档里准确说出"这次交付后，客户的国密合规诉求被满足到什么程度、哪些没有"。

- 85-100：正面列出包含/不包含清单，不包含项逐条给依据；点明"合规"在本需求中的具体所指（哪些标准、哪些条款维度）；说明为何当前边界是安全的（例如未做完整国密体系时的表述风险）。
- 60-84：范围基本清楚，但不包含项无语据，或对"合规"停留在口号式表述。
- 30-59：范围靠读者从功能描述里倒推；对 SM3/SM4/证书的沉默造成歧义。
- 0-29：完全未界定范围。

### D2 GTA 互操作契约保真度 · 权重 25
**本需求最大业务风险所在，权重最高。** 判的是：RBS 与 GTA 之间的字节级约定是否被完整、精确、无歧义地固定下来。

- 85-100：签名值编码（如 ASN.1 DER `SEQUENCE{r,s}` vs 裸 `r‖s`）、签名输入字节范围、是否预哈希、Z 值 UserId 取值、SM3 摘要对象、`alg/typ/jku/kid` 等头部字段的取值与用途、`exp=iat+expired_time` 语义与默认值、issuer 默认值、公钥格式（SPKI PEM）与分发（配置文件路径 / 无 JWKS）、时钟容差——**逐项给具体取值，并写明取值来源**（代码位置 / GTA 侧契约 / 问题池决策）。
- 60-84：覆盖了主要项，但有个别项只有定性描述（如"按标准 SM2 处理"）或未给默认值。
- 30-59：只写了"用 SM2 验签"，关键约定缺失过半。
- 0-29：未形成互操作契约，或存在与现有代码事实直接矛盾的描述。

### D3 关键规格的量化与可追溯 · 权重 15
判的是：规格是不是数字，数字有没有出处，出处在不在被评文档内可查。

- 85-100：每条规格给出目标值/阈值、测量条件、依据来源（需求原文 / 已知实现事实 / 问题池决策编号）、以及映射的用例编号；无"待定""后续明确"。
- 60-84：多数已量化，个别项依据缺失或映射不全。
- 30-59：以定性表述为主（"性能满足要求""安全可靠"）。
- 0-29：无量化规格，或规格与用例完全脱钩。

### D4 验收用例的可执行性与闭环 · 权重 15
判的是：这些用例拿给测试同学，能不能不追问作者就跑起来，跑出来的结论能不能真的证明需求被满足。

- 85-100：每条用例有场景、前提、步骤、预期结果、断言点；断言落在黑盒外表面（HTTP 响应体、CLI 输出与退出码、落盘数据）；异常场景表与异常用例逐条对应；六类对象在"覆盖对象"列标注正确；三个原始需求触点各有对应用例；验收总览的通过条件与用例表实际覆盖一致。
- 60-84：用例基本可用，但部分用例预期结果无法翻译成断言，或覆盖标注与内容不符。
- 30-59：用例只有标题与笼统预期，断言无从谈起。
- 0-29：用例缺失或与需求无关。

### D5 异常、变更影响与风险显性化 · 权重 15
判的是：坏情况有没有被想到，既有行为被改动的地方有没有交代清楚。

- 85-100：异常/冲突/兼容场景逐条列出且有处置策略；变更影响逐项给出**变更前的可核对既有行为**（接口签名、字段、默认值、错误码等，带文件位置）与变更后对比；安全相关的"做不到的事"（如无服务端吊销列表、签名随机数不可注入、泄露应急只能换钥+等过期）被作为**业务决策**显式记录并给出影响范围，而不是塞进运维备注。
- 60-84：异常场景较全，但变更影响有"原有逻辑不变"这类无信息量描述；或风险记录位置不当、影响面未说。
- 30-59：只覆盖显式异常，未覆盖兼容性与既有行为变更。
- 0-29：未分析。

### D6 模块划分、对外接口与架构一致性 · 权重 10
判的是：改动落在哪里、接口契约是否完整、是否与既有架构约束一致。

- 85-100：模块职责与改动边界清晰且与既有架构文档一致；新增/变更的对外接口给出完整契约（路径、方法、字段路径与类型、必填/可空、默认值、枚举与约束、错误码与触发条件、治理属性：认证鉴权/幂等/超时/重试/限流/版本兼容）；接口变更附变更前后差异；且明确给出"为什么不新增共享 crate"这类结构取舍的理由。
- 60-84：模块划分清楚，接口契约有字段但缺错误模型或治理属性。
- 30-59：只列了接口用途，没有契约。
- 0-29：未划分模块或与架构约束冲突。

### D7 文档自洽性与工程纪律 · 权重 5
判的是：文档能不能自证其版本与自身一致，读者不会被内部矛盾误导。

- 85-100：版本号与修订记录一致；章节编号连续无缺；占位符全部替换；图表有下方文字说明且含义与正文一致；无表头为空的表格；无"看起来对但内容为空"的章节。
- 60-84：个别小节编号或表述瑕疵，不影响使用。
- 30-59：版本/修订记录矛盾，或存在编号缺漏、空壳章节。
- 0-29：多处自相矛盾，读者无法判断哪一版是准。

## 4. 判定纪律

1. **不得因为文档很长、图表很多而加分。**
2. **不得因为文档短而扣分**——只要骨干信息齐备且准确，短文档可得高分。
3. **文档里明确写出的优点必须被计入对应维度得分**，否则该标准会奖励空模板。具体地：给出"设计意图"类取舍理由、把风险标明为业务决策而非藏进备注、对不适用章节给出可追溯依据，都属于 D1/D5/D7 的正面证据。
4. **若无法在被评文档中找到支撑某维度判定的原文**，该维度按"缺失"给分（≤30），并在 `evidence` 中写明"未找到"。
5. 最终结论必须包含：四个硬门槛的通过/不通过、七个维度的分数与理由、以及"这份文档目前能否作为下游开发与验收的唯一依据"的一句话判断。
